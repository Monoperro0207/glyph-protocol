# RFC-0005 — Server-Generated callId for Call Receipts

Status: accepted (V1).
Author: Patrick Espino.
Date: 2026-05-25.

## Summary

`CallReceipt.callId` is now always generated by the server (`randomUUID()`).
The client may optionally supply `clientCallId` for its own correlation,
but the server-owned `callId` is the authoritative audit identity. This
changes `RECEIPT_VERSION` from `0.2` to `0.3`.

## Motivation

Before this RFC, `POST /call` accepted an optional `callId` from the
request body, and the server signed whatever it received:

```json
{ "input": { ... }, "callId": "attacker-chosen-value" }
```

Because the `CallReceipt` is signed and archived, a client-controlled
`callId` introduces two problems:

1. **Forged audit identity.** An attacker who controls the `callId` can
   inject a misleading identity into the signed receipt (e.g., a duplicate
   of a legitimate `callId` from a different call), weakening audit
   correlation.
2. **No client correlation escape hatch.** A client that needs its own
   request identifier (for client-side tracing, retry deduplication, or
   UI correlation) had no dedicated field — it re-used `callId`, making
   it impossible to distinguish "server's identity for this call" from
   "client's reference to this request."

The server owns the receipt and signs it. The `callId` on the receipt
should be a server-generated, unpredictable, collision-resistant
identifier (UUID v4). The client's correlation need is separate and
should have its own dedicated, optional field.

## Specification

### Receipt version

`RECEIPT_VERSION` in `@glyphp/server` is bumped from `'0.2'` to `'0.3'`.
Receipts produced by a server on version 0.3 carry `receiptVersion: '0.3'`
and cover the changed semantics.

### callId generation

The server's `POST /call` handler now:

1. Ignores any `callId` field in the request body for receipt purposes.
2. Always generates `callId` via `randomUUID()` (v4).
3. Preserves the client-supplied value, if present, as the optional
   `clientCallId` field on the `CallReceipt`.

```typescript
// packages/server/src/server.ts — conceptual change

// Before (0.2):
const callId = body.callId ?? randomUUID();

// After (0.3):
const clientCallId = body.callId;          // optional, preserved
const callId = randomUUID();               // always server-generated
```

### CallReceipt schema change

`CallReceipt` in `@glyphp/types` gains an optional field:

```typescript
interface CallReceipt {
  // ... existing fields ...
  clientCallId?: string;  // NEW — client-supplied correlation id
}
```

The JSON Schema at `spec/schemas/call-receipt.schema.json` is updated to
include `clientCallId` as an optional string property.

### Wire behaviour

- `POST /call` with `{ "input": ..., "callId": "my-ref" }` → the server
  produces a receipt where `callId` is a fresh UUID v4 and `clientCallId`
  is `"my-ref"`.
- `POST /call` with `{ "input": ... }` (no `callId`) → the receipt has
  a fresh UUID v4 and no `clientCallId` field.
- Clients that previously read `callId` for correlation should switch to
  reading `clientCallId`. The `callId` field remains the server's
  authoritative audit identity.

### Conformance impact

The conformance suite's receipt checks validate `callId` is present and
is a string. It does not enforce a specific value or format — the check
is compatible with both 0.2 and 0.3 receipts. No conformance level
change is required.

## Migration

### For clients

| Before (0.2) | After (0.3) |
|---|---|
| Match sent `callId` against receipt `callId` | Read `receipt.callId` for audit identity, `receipt.clientCallId` for client correlation |
| Use `callId` for retry deduplication | Deduplicate on `clientCallId` (client-side) or `callId` (server-side) |

If you were comparing `receipt.callId` to the value you sent, that check
will now fail — the server always generates its own. Switch to:

```typescript
// Client-side correlation after 0.3
const myRef = "req-abc-123";
const response = await call("/glyphs/payment/authorize", {
  input: { amount: 100 },
  callId: myRef,
});
// receipt.callId       → UUID v4 (server's audit identity)
// receipt.clientCallId → "req-abc-123" (your correlation)
```

### For server operators

No action required. The bump is automatic when you upgrade
`@glyphp/server`. Existing receipts at 0.2 remain valid; new receipts
are at 0.3.

### Versioning

`RECEIPT_VERSION` follows the wire protocol versioning convention: a
minor bump (0.2 → 0.3) signals an additive, backwards-compatible change
to the receipt shape. The new `clientCallId` field is additive; existing
`CallReceipt` consumers that ignore it continue to work.
